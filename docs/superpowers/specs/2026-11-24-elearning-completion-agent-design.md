# 이러닝 완주 에이전트 설계 (작업 장부 + 자동 재개)

- 작성일: 2026-11-24
- 기준 소스: `codex/chrome-action-continuation` eed351a
- 상태: 소유자 검토 전 초안

## 1. 의도

소유자는 바쁜 실무자다. 교육 사이트 주소만 알려 주면 집합이 지시자의 목표를 스스로 추론해 결과물을 끝까지 만들어 주기를 원한다. 피클 에이전트가 하던 방식과 같다.

1. 로그인된 상태에서 이수 조건을 찾는다.
2. 강의를 끝까지 듣는다.
3. 시험을 보고 만족도 조사를 제출한다.
4. 수료 여부를 확인한다.
5. 이수증 PDF를 저장해 대화에 돌려준다.
6. 요청에 제출처가 있으면 메일 초안까지 만든다.

소유자는 이렇게 말했다. "규제가 있으면 비서가 아니다."

### 선례

소유자 휴대폰의 피클 앱(1.1.19) 대화에서 확인한 내용이다. 소유자가 열람을 허락했다.

- **사이버 연수원(acastar):** 12과목 시험과 만족도 조사를 끝내고 수료증 PDF까지 받았다.
- **한림 CS 교육(hallymedu):** 35차시, 하루 최대 8차시 과정이다. 하루 한도와 mOTP 인증 때문에 매일 정해진 시각에 이어 들어야 했다.
- **KAIRB:** 강의 3건, 총 3시간 47분이다.
  - 진도는 실제 재생 위치(`cur_time`)를 5초마다 서버에 저장하는 방식이라, 끝까지 재생해야 퀴즈가 열린다.
  - 피클은 자기 클라우드 서버에서 국내 영상 서버로 붙었다. 영상이 1.49GB짜리 1080p 단일 파일이라 0.24배속밖에 안 나와 수십 시간이 예상됐다.
- **집합의 이점:** 소유자의 국내 회선과 앱 브라우저의 로그인을 그대로 쓸 수 있다.

## 2. 소유자 결정 (2026-11-24 채팅)

1. **시험과 설문:** 시험 응시와 만족도 조사 제출도 에이전트가 직접 한다. 소유자는 이 교육들이 필수교육이 아니라고 밝혔다. 시험은 100점을 목표로 푼다.
2. **승인 범위:** 요청에 명시된 제출은 그 요청 자체를 승인으로 본다.
   - 별도 승인은 되돌리기 힘든 일에만 받는다. 결제, 메일·메시지 발송, 전화, 회원 탈퇴가 여기에 해당한다.
   - 소유자가 피클에서 고른 "되돌리기 힘든 일만 허락 받기"와 같은 기준이다.
3. **유지하는 원칙:**
   - 비밀번호·mOTP·본인인증은 소유자가 직접 입력한다. 기존 보안 로그인 카드와 휴대폰 인증 넘기기를 쓴다.
   - CAPTCHA나 매크로 탐지는 우회하지 않는다.
   - 진도 기록을 조작하지 않는다. 배속 우회나 재생 위치 위조 없이 정상 속도로 재생한다.
4. **재생 위치:** 휴대폰 앱 브라우저에서 재생한다. 이후 소유자 지시에 따라 모바일 데이터와 배터리에서도 진행한다.
5. **방식:** 작업 장부 + 자동 재개(이 문서의 3장, 접근법 1).

## 3. 접근법

| 접근법 | 내용 | 장단점 | 결과 |
|---|---|---|---|
| 1. 작업 장부 + 자동 재개 | 모델이 사이트를 둘러보고 과정 × 항목(강의·시험·설문·이수증) 장부를 쓴다. 실행마다 장부를 읽고 처리한 뒤 갱신한다. 긴 대기는 실행을 접고, 호스트가 조건을 지켜보다가 같은 목표를 이어서 실행한다. | 앱 종료·재부팅을 견딘다. 대기 중에는 모델 비용이 없다. 대기·재개 장치를 새로 만들어야 한다. | **채택** |
| 2. 한 번의 긴 실행 | 목표 한도(30분·144회)를 시간 단위로 늘리고, 모델이 영상 종료까지 직접 관찰한다. | 만들기 가장 쉽다. 하지만 앱이 종료되면 처음부터 하고, 하루 한도·인증 대기를 넘지 못하며, 관찰 중에도 모델 비용이 든다. | 기각 |
| 3. 사이트별 고정 스크립트 | 세 사이트의 순서를 미리 짠다. | 세 사이트에서는 안정적이다. 새 사이트마다 다시 만들어야 하고, 프로젝트 원칙(모델 해석 우선, 고정 시나리오 금지)에 어긋난다. | 기각 |

## 4. 목표·비목표·반목표

### 목표

- 대화 하나로 시작한다. 예: "이 사이트 교육 다 이수하고 이수증 줘. 끝나면 김영진 사원에게 메일 보낼 준비해 줘."
  - 모드나 분류는 고르지 않는다. 기존 단일 대화 원칙을 따른다.
- 집합이 다음을 스스로 해낸다.
  - 로그인 상태 확인과 인증 넘기기
  - 이수 조건 발견
  - 장부 작성
  - 강의 재생, 시험, 설문
  - 수료 재확인과 이수증 저장
  - 최종 보고
- 여러 날짜에 걸친 과정을 이어서 끝낸다.
  - 하루 한도가 있으면 다음 날 이어서 한다.
  - mOTP 같은 인증은 소유자가 마치면 바로 재개한다.
- 진행 상황이 대화에 보인다.
  - 장부 요약 예: "KAIRB 1/3 · 31%"
  - 대기 이유와 다음 재개 시각
- 완료 보고에는 과정마다 사이트에서 관찰한 수료 근거와 저장한 파일을 붙인다.

### 비목표

- PC에서 재생하지 않는다.
- 여러 계정을 동시에 다루지 않는다.
- 사이트별 고정 스크립트를 만들지 않는다.
- 결제가 필요한 신규 수강신청은 자동으로 하지 않는다. 결제 승인 대상이다.

### 반목표 (기술적으로 돌아가도 실패로 본다)

- 사이트의 수료 표시나 저장 파일 없이 "완료"라고 보고한다.
- 실제로 멈춘 상태인데 "백그라운드에서 계속 중"이라고 말한다. 기존 규칙이다.
- 진도를 조작하거나 탐지를 우회한다.
- 키워드나 문구로 요청을 분류해 이 흐름을 켠다. 프로젝트 금지 사항이며, 모델 해석이 같은 동작을 골랐을 때만 실행한다.
- 소유자 비밀번호나 인증번호가 모델·로그·Git에 남는다.

## 6. 설계

### 6.1 작업 장부 (`GoalProgressLedger`)

목표 하나에 장부 하나를 둔다. 기존 목표 노트처럼 암호화해 저장하고, 수정할 때는 CAS(`updatedAt`)로 충돌을 막는다.

- **항목 필드:**
  - `id`
  - `course`
  - `unit`(차시·과목)
  - `kind`: `lecture` | `quiz` | `survey` | `certificate` | `condition` | `other`
  - `status`: `todo` | `active` | `waiting` | `done` | `blocked`
  - `note`(200자 이하)
  - `evidence`
- **전체 필드:**
  - `requirements`(발견한 이수 조건 원문 요약, 2,000자 이하)
  - `dailyLimit`(있으면)
  - `deadline`
- **한도:** 항목 300개, 전체 64KB.
- **도구:** `read_goal_progress`(LOW), `update_goal_progress`(LOW).
  - 모델은 항목을 추가하거나 상태를 바꾼다.
  - 호스트는 스키마·한도·소속 목표를 검증한다.
- **`done` 조건:** 이번 목표 실행에서 실제로 관찰한 도구 결과에 연결된 근거가 있어야 한다. 기존 `GoalCriterion VERIFIED` 규칙과 같다.
  - 강의: 같은 플레이어의 `BrowserMediaProgress` 종료, 또는 사이트의 진도 100% 표시 관찰
  - 시험: 제출 후 점수나 합격 표시 관찰
  - 설문: 제출 후 완료 표시 관찰
  - 이수증: 저장된 파일 해시
- **목표 기준과의 관계:** 기준(criteria)은 "과정 X 수료 표시 확인", "이수증 PDF 저장"처럼 상위 조건만 둔다. 장부는 세부 진행이다.

### 6.2 호스트 대기와 자동 재개 (`GoalWait`)

모델이 기다려야 할 때는 도구 `wait_for_goal_condition`(LOW)으로 실행을 접는다. 목표는 새 상태 `WAITING`이 되고, 일시정지 사유 `WAITING_CONDITION`을 기록한다.

**조건 종류 (하나만 고른다):**

1. `media_end`
   - 대상: 현재 앱 브라우저의 같은 플레이어
   - 호스트 감시기가 기존 미디어 관찰(`app-web-agent.js` media read)을 30초 간격으로 부른다. 모델은 호출하지 않는다.
   - 깨우는 경우:
     - `ENDED`
     - 진행 정지 10분
     - 플레이어나 페이지가 사라짐
     - 로그인 만료
     - 상한 6시간
   - 재생 중에는 기존 `AgentRunService` 계열 포그라운드 서비스를 유지하고 `PARTIAL_WAKE_LOCK`을 건다.
   - 전원이나 접속 방식이 바뀌어도 같은 영상의 실제 재생 상태를 확인한다. 정지나 연결 문제는 관찰된 결과로 처리한다.
2. `at_time`
   - ISO 시각에 깨운다. 예: 하루 한도가 풀리는 다음 날 09:00
   - 기존 `ScheduledReadWork`의 WorkManager 1회성 작업을 일반화한다.
   - 예약은 접속 방식 및 전원에 관계없이 깨어나며, 해당 시점의 실제 사이트 접속과 재생 상태를 확인한다.
3. `owner_auth`
   - 소유자가 보안 로그인 카드나 휴대폰 인증 화면을 마치면 깨운다.
   - 기존 `PHONE_BROWSER_AUTH_REQUIRED` 대기를 같은 목표 재개로 잇는다.

**재개:**

- 같은 목표 ID, 장부, 원래 요청 권한(클라우드 권한 revision, 위임 범위)으로 다음 구간을 큐에 넣는다.
- 권한 revision이 바뀌었으면 승격하지 않고 보존한다. 기존 규칙이다.
- 같은 목표의 대기는 하나만 둔다.
- 재개는 1회만 한다. 같은 조건으로 바로 다시 실패하면 소유자에게 보고하고 멈춘다.

**예산 변경:**

- 지금의 누적 30분·144회를 '활동 구간 예산'으로 바꾼다.
  - 깨어난 활동 1회당: 30분·144회·8구간
  - 대기 시간은 예산에 넣지 않는다.
- 목표 전체 상한은 새로 둔다.
  - 기간: 시작 후 14일 또는 사이트 마감일 중 이른 날
  - 깨움: 하루 최대 12회, 전체 120회
- 네이티브 예산 검사(`NativeGoalBudgetStop`)도 같은 의미로 바꾼다.

**대화 표시:** 작업 카드에 다음을 보인다.

- 장부 요약
- 대기 이유
- 다음 재개 시각이나 조건
- 중지 버튼

정말 멈춘 경우에는 "멈춤"으로 표시한다.

### 6.3 요청 위임 제출 (`DelegatedSubmission`)

- **범위 정하기:** 모델이 요청을 해석해 목표의 `constraints`에 위임 범위를 적는다.
  - 대상 사이트의 출처(origin) 목록
  - 동작 종류: `lesson_complete`, `quiz_submit`, `survey_submit`
  - 이 범위는 목표 카드에 그대로 보인다.
- **승인:** 소유자가 그 목표를 시작하거나 요청에서 바로 시작하면, 그것을 위임 승인으로 기록한다. 기존 `start_goal`은 소유자의 명시 요청 때만 실행된다.
- **클릭 판정:** 위임 범위 안의 출처에서 `WebAgentPolicy.riskyControl`에 걸린 클릭이라도, 아래를 모두 만족하면 클릭 단위 승인을 생략한다.
  1. 라벨이 제출·확인·완료·다음·응시·submit·confirm 계열이다.
  2. 결제·구매·송금·이체·보내기·전송·삭제·탈퇴·해지·가입 계열 단어가 없다.
  3. 같은 스냅샷 재검증을 통과한다.
- **위임하지 않는 것:** 결제, 메일 발송, 탈퇴는 위임 범위와 상관없이 기존 승인을 받는다.
- **설문 의견:** 만족도 등 의견 문항에는 요청에 적힌 소유자의 평가를 입력한다. 요청에 없으면 시작할 때 한 번 묻는다. 이건 이번 설계의 결정이고 소유자가 바꿀 수 있다.
- **시험:** 장부와 관찰한 강의 내용, 모델 지식으로 푼다.
  - 제출한 뒤 점수를 읽는다.
  - 목표 점수에 못 미치고 사이트가 재응시를 허용하면 다시 푼다. 횟수는 사이트 한도와 1회 추가 중 작은 쪽이다.

### 6.4 브라우저 보강 (Codex 소유 파일)

1. `setMediaPlaybackRequiresUserGesture(false)`: 앱 에이전트 WebView에만 적용한다. 재생은 모델이 실제 재생 버튼을 누르는 방식을 유지한다.
2. 화면이 꺼지거나 앱이 백그라운드에 있어도 WebView를 일시정지하지 않는다. `onPause`나 `pauseTimers`를 부르지 않는다. 실제 기기 검증이 먼저다(7장 위험 1).
3. **소리 기본값:** 재생 중 소리는 시스템 미디어 볼륨을 그대로 둔다. 플레이어의 음소거 버튼은 사이트 화면 조작으로만 쓴다. 볼륨이 0이어도 진도는 쌓인다.
4. **새 창:** `setSupportMultipleWindows(true)`와 `onCreateWindow`로 새 창을 같은 정책의 두 번째 오프스크린 WebView에 연다. 최대 2개다.
   - 관찰 결과에 `window` 식별자를 붙인다.
   - 새 창이 닫히면 원래 창으로 돌아간다.
5. **이수증 캡처:** 우선순위 순서대로 시도한다.
   1. 기존 `.pdf` 원본 저장
   2. 인쇄형: 현재 창의 `createPrintDocumentAdapter`로 PDF를 만든다.
   3. blob·POST 다운로드: `DownloadListener`와 페이지 안 `fetch`를 쓴다. 같은 출처만 받고, `%PDF-`로 시작해야 하며 10MB 이하여야 한다.
   - 모두 `filesDir/exports/artifact-<uuid>.pdf`에 원자적으로 저장하고, 해시와 페이지 수를 검증한다.
   - 인쇄형은 원본이 아니라 "화면에서 만든 PDF"로 표시한다.

## 7. 위험과 먼저 할 검증

1. **화면 꺼짐 재생 (먼저 확인):** 오프스크린 WebView가 화면이 꺼진 상태나 백그라운드에서 영상을 계속 재생하고 진도를 쌓는지 실제 휴대폰에서 확인한다.
   - KAIRB 1개 강의를 10분 동안 돌려 사이트 진도율이 오르는지 본다.
   - 안 되면 대안을 쓴다. 집합 화면을 켜 둔 전경 재생, 또는 화면 유지 배지를 WebView 재생에도 확장하는 방식이다.
2. **제스처 없는 재생과 탐지:** 사이트가 제스처 없는 재생이나 백그라운드 재생을 막는지 확인한다. 막으면 우회하지 않고 소유자에게 전경 재생을 안내한다.
3. **데이터와 배터리:** 용량이 큰 영상은 모바일 데이터와 배터리를 사용할 수 있다. 실기에서 재생과 대기 상태를 관찰한다.
4. **위임 오판:** 위임 범위 밖 출처와 위험 단어 조합을 거부하는 회귀 시험을 둔다.
5. **장부 신뢰:** 모델이 쓴 `done`은 근거 연결이 없으면 거부한다.

## 9.1 설계자 판단 (빌더 검토 질문에 대한 답, 소유자가 바꿀 수 있음)

1. **재개 때의 클라우드 판단**
   - 재개는 장부·목표·직전 관찰 요약을 들고 새 클라우드 세션으로 시작한다. 기존 목표 구간과 같은 방식이다. PC의 이전 대화는 이어 쓰지 않는다.
   - 깨울 시각에 PC나 브리지가 없으면 대기를 유지한다. 15분 간격으로 최대 8회 다시 시도하고, 그래도 안 되면 소유자에게 알린 뒤 다음 깨움을 기다린다.
   - 이 재시도는 깨움 횟수에도, "재개 1회" 규칙에도 세지 않는다.
   - 휴대폰 로컬 모델로 판단을 대신하지 않는다.
2. **무인 재생 시작**
   - 완전 무인 시작을 기본으로 한다. Android 12 이상에서 백그라운드 포그라운드 서비스를 시작하려면 집합이 배터리 최적화 예외 상태여야 한다.
   - 예외는 소유자가 Android 시스템 동의 화면에서 한 번 허용한다. 기존 `BackgroundRunExemption` 안내를 쓴다.
   - 예외가 없으면 예약 시각에 알림을 띄운다. 소유자가 알림을 누르면 재생을 시작한다.
   - 서비스 유형은 재생 중에만 `mediaPlayback`을 추가하는 방향으로 Codex와 정한다.
3. **분담:** 사무실 채팅방 #66의 Codex 회신으로 확정한다. 확정 전에는 Claude가 새 파일 범위만 작성한다.
4. **앱 종료와 재부팅**
   - 대기 기록에 마지막 강의 주소, 플레이어 위치 서명, 장부 항목 ID를 저장한다.
   - 재부팅 뒤에는 WorkManager 복원이 그 주소를 앱 브라우저로 다시 열고 같은 강의인지 관찰한다.
   - 같은 강의면 재생 버튼 누르기를 모델에 맡긴다. 이를 위해 `owner_auth`나 `media_end` 재개로 1회 깨운다.
   - 다르거나 로그인이 만료됐으면 해당 사유로 깨운다.
   - 대기 중 WebView 수명은 실행이 아니라 대기 장치(포그라운드 서비스)에 묶는다. 단일 WebView 인스턴스는 유지한다.
5. **위험 1 실험의 순서**
   - 화면 꺼짐 재생 실험을 가장 먼저 한다. 실험 전에는 `media_end` 감시기와 웨이크락을 만들지 않는다.
   - 장부, 위임, 이수증 캡처, 스킬은 실험과 무관해서 병렬로 진행한다.
   - 실험이 실패하면 전경 재생을 기본으로 한다. 집합 화면에 플레이어를 띄우고 화면 유지를 건다. 기존 화면 유지 배지 방식을 WebView 재생에도 확장한다.
6. **매일 인증이 필요한 과정**
   - `at_time`으로 깨운 실행이 인증 화면을 만나면 `owner_auth` 대기로 넘어가고 소유자에게 알림을 보낸다.
   - 이 전환은 같은 깨움 1회로 센다.
   - 소유자가 그날 21:00까지 응답하지 않으면 다음 날 같은 시각으로 `at_time`을 다시 건다. 이것은 새 깨움 1회다.
