# 집순이 채팅 영역 재구성·디자인 고도화 계획 (피클 참조)

- 작성일: 2026-11-24
- 기준: `codex/chrome-action-continuation` 계열 e637973 (Codex의 eba81d4 "주요 화면 다듬기" 포함)
- 상태: 소유자 검토 전 계획안. 코드 변경 없음.

## 1. 목적

소유자 지시: "UI, UX, 구조, 기능, 채팅 영역의 효과적·효율적 재구성과 전체 디자인 고도화 계획을 세워라. 피클이 아주 잘된 경우이니 참조하라."

목표는 세 가지다.

- 집순이가 바쁜 소유자의 일을 맡아 끝내는 비서로 보여야 한다. 기능 목록처럼 보이면 안 된다.
- 대화는 가볍게 읽히고, 작업은 한눈에 상태가 보여야 한다.
- 결과물은 바로 찾을 수 있어야 한다.

## 2. 피클에서 관찰한 것

자료는 두 가지다.

- 소유자 휴대폰의 피클 1.1.19 화면 구조. 2026-11-24에 ADB 접근성 트리로 읽었다. 대화 내용은 기록하지 않았다.
- 공개 리뷰

### 2.2 잘된 점 (집순이에 가져올 것)

1. **대화는 가볍게, 작업은 카드로.** 답은 평문이고 작업은 한 줄 카드다. 자세한 내용은 눌러서 본다.
2. **진행 중인 큰 일이 항상 보인다.** 헤더 한 줄에 떠 있어서, 그동안 다른 얘기를 해도 일이 사라지지 않는다.
3. **결정은 버튼으로.** 선택지와 추천안을 주니 소유자는 한 번 누르면 된다.
4. **결과물은 보관함에 모인다.** 이수증 같은 파일을 날짜별로 다시 찾는다.
5. **한 일·예약한 일 기록**이 신뢰를 만든다.
6. **능동성:** 아침 브리핑, 후속 제안, 일정 겹침 경고

### 2.3 피클의 약점 (따라 하지 않을 것)

- 확인 없이 범위를 넓혔다(매장 두 곳에 전화, 별점 임의 설정).
- 상태 검증 없이 완료를 보고했다(스토어 196개가 노출 제한이었는데 "판매중"으로 보고).
- 승인 흐름이 앱 구조가 아니라 지시문에 의존한다는 지적이 있다.
- 사용량 표시가 직관적이지 않다는 지적이 있다.
- "N명이 맡겼어요" 같은 사회적 증거 숫자: 집순이에는 실제 근거가 없으므로 만들어 내지 않는다.

## 3. 현재 집순이 진단 (e637973, 휴대폰 화면 확인 포함)

### 3.1 채팅

- **답변이 무겁다.** 답마다 "집순이" 아바타·이름표가 붙고, 테두리 있는 큰 상자에 들어간다. 한 화면에 보이는 대화가 적다.
- **작업 카드가 너무 크다.** 일시정지 카드 하나가 화면의 약 1/4을 차지한다(빨간 테두리, 아이콘 타일, 단계 3줄, 작업 내역).
  - 단계 문구 "사이트 화면 확인 · 실행 결과 기록"은 사람이 읽기에 어색하고 내부 용어가 남아 있다.
  - 메시지에 붙지 못한 카드는 아래 floating 영역에 따로 모인다(`Conversation.tsx:262-300`).
- **입력창 위의 "기기 안에서 실행" 문구**가 무엇을 뜻하는지 불분명하다.
- **헤더의 모델 선택("자동")** 이 크게 보인다. 소유자에게는 기술적 선택지다.
- **승인이 대화 밖 네이티브 창으로 뜬다.** `ActionApprovalDialog`(`MainActivity.kt:811`) 때문에 흐름이 끊긴다. 로그인 카드는 WebView 빈자리 위에 Compose 오버레이로 겹쳐서(`NativeWebsiteOverlay`) 키보드 높이 동기화가 불안하다.
- **같은 개념이 두 벌 있다.** 작업 기록이 React `TaskCard`와, 쓰이지 않는 Compose `InlineRunActivityCard`/`ChatWorkspace`에 따로 있다. 사무실·직원방 React 경로도 남아 있다(`!singleConversation`).
- **결정 칩 계약이 없다.** 모델이 "어떻게 할까요?"를 글로 묻고 소유자가 직접 타이핑한다.

### 3.2 구조와 탐색

- 탭 이름은 피클과 같다(기본 채팅·둘러보기·보관함·나의 집순이). 내용은 다르다.
  - 둘러보기 = 기능 목록(`OfficeCapabilityShelf`, Compose)
  - 보관함 = 대화 기록 성격
  - "한 일 / 예약한 일" 같은 작업 기록 화면과, 파일 중심 보관함이 없다.
- 채팅은 React(WebView)이고 나머지 화면은 Compose다. 색은 맞췄지만 간격, 글자 크기, 모서리 규칙은 따로 정의돼 있다.

### 3.3 디자인 시스템

- "Sunlit Porcelain" 밝은 단일 테마가 소유자 지시(2026-11-19)이고, 검은 화면은 금지다.
- 토큰이 이중이다. `styles.css`와 `ZipHapDesign.kt`에 따로 있다.
- 간격 토큰이 없고 px 값이 직접 박혀 있다.
- 죽은 다크 분기가 있다. `App.tsx:120`이 `data-theme`를 계산하지만 효과가 없다.
- `docs/design-system.md`는 옛 어두운 팔레트 그대로라 현실과 정반대다.

## 4. 원칙

1. **대화 하나는 유지한다.** AGENTS.md와 `conversation-workflow.ko.md`를 따른다. 작업 분류 탭이나 모드 선택을 추가하지 않는다.
2. **말은 평문, 일은 카드, 결정은 버튼.**
3. **근거가 보이는 완료.** "완료" 표시는 호스트가 검증한 결과에만 붙인다. 검증하지 못하면 "확인 필요"로 표시한다. 피클의 약점을 반복하지 않는다.
4. **보안 경계는 앱 구조로 둔다.** 승인과 비밀값 입력은 호스트가 발급한 토큰과 스냅샷에 묶는다. UI를 바꿔도 경계는 약해지지 않는다.
5. **밝은 단일 테마, 역할 색 고정.** 코발트=행동, 코랄=확인 필요, 민트=완료, 선샤인=대기, 라일락=협업
6. **한 번 만들어 양쪽에서 쓴다.** 토큰은 원본 하나에서 CSS와 Compose를 생성한다.

│ └──────────────────────────────────┘ │

### 5.2 작업 카드 한 가지 체계 (`WorkCard`)

- **상태와 색:**

| 상태 | 표시 | 색 |
|---|---|---|
| 진행 중 | 진행률 또는 경과 시간 | 코발트 |
| 대기(예약·영상 종료·인증) | 다음 재개 시각과 조건 | 선샤인 |
| 확인 필요(승인·답변) | 해야 할 일 한 줄과 버튼 | 코랄 |
| 완료 | 근거 요약("수료 확인됨", "파일 저장됨") | 민트 |
| 실패·중단 | 사실 그대로 한 줄 | 회색과 코랄 |

- **한 줄 카드:** 아이콘(작업 종류) + 제목 + 상태·시각 + ›. 카드는 원래 요청 메시지 바로 아래에 붙인다. floating 영역은 없앤다.
- **누르면 하단 시트**가 열린다. 단계 목록, 관찰 근거, 장부(이러닝이면 과정별 진행), 중지·재개 버튼이 있다.
- **단계 문구는 사람 말로 바꾼다.** 내부 evidence 코드를 한국어 표현으로 옮기는 매핑 표를 둔다. 예: "사이트 화면 확인 · 실행 결과 기록" → "사이트 화면을 읽었어요".
- **진행 중 큰 작업**(목표·대기 중인 일)은 헤더 작업 줄에도 보인다.
  - 여러 개면 "작업 2개 ›"로 표시한다.
  - 대기 중이면 "멈춤이 아니라 21:00에 이어서"처럼 실제 상태를 말한다. 실제로 멈췄으면 "멈춤"으로 표시한다.

### 5.3 대화 안 카드 (기존 네이티브 창 대체)

| 카드 | 렌더 | 경계 |
|---|---|---|
| 승인 카드 (LOW·MEDIUM) | React 카드: 무엇을, 어디에, 금액·수신자, [진행] [취소] | 호스트가 발급한 승인 토큰·스냅샷·epoch를 브리지로 다시 대조한다. 토큰이 바뀌면 거부한다. |
| 승인 카드 (HIGH: 발송·결제·삭제·탈퇴) | 대화 안 카드 + 확정은 네이티브 확인(지금처럼) | 이중 확인을 유지한다. |
| 보안 입력 (로그인·인증번호) | 대화 안 카드 자리에 네이티브 입력란을 띄운다. 키보드가 열리면 하단 시트로 올라온다. | 값은 React·모델로 가지 않는다(기존 그대로). |
| 결제 카드 정보 | 대화 안 카드에서 사이트의 결제 화면을 앱 브라우저로 연다. 소유자는 사이트 화면에 직접 입력한다. | 집순이는 카드번호를 받거나 저장·주입하지 않는다(기존 원칙). 결제 확정은 HIGH 승인이다. |

**입력 뒤 카드 전환 (소유자 결정 2026-11-24)**

- 로그인·인증번호·결제 입력이나 승인이 끝나면, 같은 카드가 **작업 단계 안내 카드**로 바뀐다.
- 이전 입력칸과 버튼은 다시 나타나지 않는다. 값은 카드에 남지 않고, 승인 토큰은 1회용이다.
- 바뀐 카드에는 다음을 보인다.
  - 처리 결과: "로그인 완료 · 3분 전", "결제 승인함 · 대기"
  - 이어지는 단계: 예) "수강 목록 확인 중 → 1번 강의 재생"
  - 현재 상태
- 이후 진행은 같은 카드에서 갱신된다. 소유자가 다시 입력해야 하면(세션 만료, 새 인증번호) 새 입력 카드를 띄운다. 끝난 카드를 다시 쓰지 않는다.
- 이렇게 하면 네이티브 창처럼 입력이 한 번에 닫히면서, 대화에는 무엇을 했는지 기록이 남는다.
| 결정 칩 | 모델이 낸 선택지 2~4개(각 40자 이하)를 칩으로 보인다. 추천은 하나만. | 누르면 그 글이 **일반 사용자 메시지**로 전송된다. 칩이 도구나 권한을 실행하지 않는다. 키워드 라우팅 금지 원칙에 맞는다. |
| 연결 카드 | 기존 `ChatConnectionCard`를 같은 카드 체계로 바꾼다. | 기존 동의 흐름을 유지한다. |
| 결과 파일·링크 | 파일 카드(이름·쪽수·용량·열기·공유), 링크 미리보기 | 공유·내보내기는 소유자가 직접 한다(기존 원칙). |

### 5.4 메시지 표현

- 에이전트 답은 상자 없이 평문으로 쓴다. 아바타와 이름은 연속 묶음의 첫 메시지에만 붙인다.
- 날짜 구분선과 상대 시각을 둔다.
- 사용자 말풍선은 연한 코발트로 하고 오른쪽에 정렬한다.
- 복사와 메뉴는 길게 누르기로 옮겨 상시 아이콘을 줄인다.

### 5.5 입력창

- 구성: [+] (첨부·스킬·사진·파일) · 입력란 · [🎙 받아쓰기] · [↑ 보내기]
- 실행 중일 때는 "다음에 보내기"와 "추가 지시"를 유지한다.
- "기기 안에서 실행"은 + 시트 안의 "처리 위치·모델" 항목으로 옮긴다. 헤더의 모델 선택도 같은 곳으로 옮긴다. 개인정보 모드처럼 의미가 큰 상태만 입력란 왼쪽에 작은 칩으로 표시한다.
- 음성 대화 버튼은 받아쓰기 옆에 둔다(1단계, 6.1).

### 5.6 탭 재정의

| 탭 | 새 내용 | 출처 |
|---|---|---|
| 채팅 | 위의 대화 | React |
| 둘러보기 | 분류 칩, 예시 작업 카드(누르면 입력란에 초안), **"집순이의 제안"**(어제 대화 후속, 일정 겹침, 마감 임박) | 기존 `OfficeCapabilityShelf` 개편 + 브리핑 재사용 |
| 보관함 | **파일 / 미디어** 탭, 날짜별 결과물(이수증 PDF, 생성 이미지, 보고서). 파일마다 원래 대화로 가기·공유 | `filesDir/exports`, `ChatResultPreviews` |
| 나의 집순이 | 상단: **한 일 / 예약한 일** 기록(작업 제목·요약·상태·시각, 예약 대기 해제). 아래: 연결된 서비스 수, 개인정보·권한, 처리 위치·모델, 사용량(클라우드 구독 상태) | 작업 기록, `GoalWait` 대기, 설정 |

- 대화 기록과 검색은 서랍 메뉴에 둔다(피클과 같다).

### 5.7 디자인 시스템 정비

- **토큰 원본 하나:** `design/tokens.json`(색·글자·간격·모서리·그림자·움직임)
  - 빌드 때 `web-ui/src/tokens.css`와 `ZipHapTokens.kt`를 생성한다.
  - 간격은 4pt 단위로 둔다(4, 8, 12, 16, 20, 24, 32).
  - 글자 크기: 캡션 12 · 보조 13 · 본문 15 · 소제목 17 · 제목 20 · 화면 제목 24
- **컴포넌트 목록:** 말풍선, 평문 답, WorkCard, 하단 시트, 결정 칩, 파일 카드, 링크 카드, 연결 카드, 탭 바, 헤더 작업 줄, 빈 상태, 오류 줄
  - React와 Compose를 같은 이름과 규칙으로 맞춘다.
- **캐릭터 콘셉트 (소유자 결정 2026-11-24: "조금 더 귀엽게, 집순이 느낌")**
  - 집에서 뒹굴며 편하게 일을 처리해 주는 친구라는 인상을 준다.
  - **모양:** 동글동글한 얼굴과 몸. 동물 귀 모양 후드가 달린 잠옷이나 후드티를 입는다.
  - **소품:** 담요, 쿠션, 머그컵. 상황에 따라 노트북이나 휴대폰을 든다.
  - **얼굴:** 볼 터치(연한 분홍)를 넣는다. 기본 눈은 살짝 졸린 반달눈이다.
  - **선과 색:** 굵고 둥근 선. 파스텔 채움. 그림자는 넣지 않는다.
  - **작게 써도 알아보게:** 헤더 32px에서도 후드 귀와 볼 터치가 보이는 단순한 모양이어야 한다.
  - **상태 표현**
    - 작업 중: 노트북을 두드린다.
    - 대기: 담요를 덮고 졸고 있다. 옆에 재개 시각을 쓴 말풍선이 뜬다.
    - 완료: 머그컵을 들고 웃는다.
    - 확인 필요: 손을 들고 놀란 얼굴이다.
  - 기존 마스코트(`ziphap-mascot.png`)는 이 캐릭터로 교체한다.
  - **시안 3종을 모두 넣고 소유자가 고른다 (소유자 결정 2026-11-24).**
    - 종류: A 곰돌이 후드, B 고양이 후드, C 토끼 후드
    - 시안 캔버스: https://claude.ai/artifact/THpfXm374ovMvoKKpyQac5 (소유자 비공개)
    - 기본값: A 곰돌이 · 버터 · 기본 표정
    - 첫 대화 안내에서 "집순이 모습 고르기"를 선택 단계로 보여 준다. 건너뛰면 기본값을 쓴다. 나중에 나의 집순이 > 캐릭터에서 언제든 바꾼다.
  - **구현 원본:** 시안 캔버스의 `Character` 부품을 기준으로 한다(viewBox 200×200, 층 구조: 귀 → 몸·후드·얼굴 → 표정 → 상태 소품). 이 원본에서 React SVG 부품과 Compose 그리기(VectorDrawable 또는 Canvas) 양쪽을 만든다. 귀·색·표정·상태가 모두 매개변수다.
- **캐릭터 (소유자 결정 2026-11-24: 색과 표정을 직접 선택)**
  - 집순이 얼굴을 헤더, 빈 상태, 작업 완료 반응, 음성 대화 화면에 일관되게 쓴다.
  - 소유자는 나의 집순이 > 캐릭터에서 다음을 고른다.
    - 시안 3종: 곰돌이·고양이·토끼
    - 색 8가지: 버터·복숭아·딸기우유·하늘·말차·회색곰·코코아·눈송이
    - 표정 6가지: 기본 반달눈·웃음·집중·놀람·졸림·윙크
  - 선택값은 기기에 저장한다.
  - 표정은 상태에 따라 자동으로 바뀐다(작업 중=집중, 완료=웃음, 확인 필요=놀람). 소유자가 고른 표정은 평상시 기본값이다.
  - 얼굴은 벡터(SVG/VectorDrawable) 한 벌로 만들어 React와 Compose가 함께 쓴다.
- **문서:** `docs/design-system.md`를 새 시스템으로 바꾼다. `ziphap-design-system.ko.md`의 이전 판 부분은 삭제한다. 죽은 다크 분기도 제거한다.
- **접근성:**
  - WCAG AA 대비를 유지한다.
  - 글자 크기 200%에서 겹침이 없어야 한다.
  - TalkBack 라벨(작업 카드 상태 읽기)을 붙인다.
  - 움직임 줄이기 설정을 따른다.

## 6. 소유자 결정

1. **승인 카드 위치 (결정 2026-11-24: 대화 안 카드).** 입력·승인 뒤 작업 단계 안내 카드로 바뀌고, 입력칸은 다시 나오지 않는다(5.3). 아래는 결정 당시 비교 내용이다.
   - 기본안: LOW·MEDIUM은 대화 안 카드로 한다. HIGH는 대화 안 카드에 네이티브 확인을 한 번 더 거친다.
   - 대안: 전부 지금처럼 네이티브 창으로 둔다.
   - 차이:
     - 네이티브 창은 화면 전체를 덮는 팝업이다. 대화가 가려지고, 닫으면 기록이 남지 않는다.
     - 대화 안 카드는 메시지처럼 대화 흐름에 남는다. 앞뒤 맥락이 보이고, 처리 뒤 "승인함 · 3분 전"으로 기록된다.
   - 보안 검증은 둘 다 호스트가 발급한 토큰으로 같게 한다.
2. **캐릭터 (결정 2026-11-24):** 소유자가 색과 표정을 직접 고른다(5.7).
3. **음성 대화 (결정 2026-11-24):** 앞당겨 넣는다(1단계 병행, 6.1). 휴대폰의 삼성 도구를 쓴다.

### 6.1 음성 대화 설계 (1단계 병행)

- **휴대폰에서 확인한 것 (2026-11-24, ADB):**
  - 기본 음성 출력 엔진이 삼성 TTS(`com.samsung.SMT`)이고, 한국어 음성 팩(`lang_ko_kr_r00`)이 설치되어 있다.
  - 빅스비 기기 내 인식(`bixby.ondevice.kokr`)과 통화 도우미(`callassistant`)도 있지만, 외부 앱용 공개 API가 없어 쓰지 않는다.
  - 칩은 Exynos 2600(`s5e9965`)이다. 삼성 AICore(`com.samsung.android.aicore`, samsungslsi 2026-10-15)와 Google AICore가 설치되어 있다. ML Kit GenAI 음성 인식 Advanced 모드의 지원 대상(S26/Exynos 2600)이다.
- **한국어 인식 엔진 선택 (소유자 지시 2026-11-24: "한국어 인식 성능이 가장 좋은 것")**
  - 조건: 기기 안에서만 동작해야 한다(AGENTS.md: 음성 전사는 로컬). 새 유료 API는 쓰지 않는다. 라이선스는 Apache, MIT, 무료 플랫폼 SDK여야 한다.

| 용도 | 선택 | 근거 | 상태 |
|---|---|---|---|
| **음성 대화 (실시간)** | ML Kit GenAI Speech Recognition **Advanced** (ko-KR, 기기 내 Gemini Nano, NPU) | 후보 중 유일하게 스트리밍 부분 결과, 휴대폰 NPU 가속, 앱 메모리 부담 없음을 모두 갖췄다. 대상 기기를 지원한다. | 이미 연결됨(`SystemAsrEngine`, `MODE_ADVANCED`). 한국어 정확도는 공개 수치가 없어 아래 실측이 필요하다. |
| **정확도 우선 전사** (긴 받아쓰기, 녹음 파일, 대화 후 재확인) | **Qwen3-ASR 1.7B** (Apache-2.0) | 공개 수치 중 한국어 최고. 벤더 보고 FLEURS-ko 2.57, Common Voice-ko 5.88. Whisper large-v3의 FLEURS-ko 약 5.3보다 좋다. | 이미 연결됨(파일 전사). 이 휴대폰의 이전 실측(합성 1문장, 8kHz)은 처리 시간이 음성 길이의 약 3.4배, 메모리 4.5GB였다. 실시간 대화에는 쓰지 않는다. |
| 속도 우선 전사 | Qwen3-ASR 0.6B | FLEURS-ko 3.72. 이전 실측은 음성 길이와 비슷한 처리 시간, 메모리 2GB | 이미 연결됨 |
| 대화 대체 (ML Kit Advanced 미준비 시) | 이미 설치된 Android 기기 내 음성 인식(`createOnDeviceSpeechRecognizer`, 기본 인식 서비스는 Google). 그다음 ML Kit Basic 모드 | 새로 설치할 것이 없다. | 연결이 필요하다(코드만). |

- **음성 결정 (소유자 2026-11-24): 이미 설치된 것으로 해결한다.**
  - 실시간 음성 대화: 듣기는 ML Kit Advanced(설치된 AICore 사용), 말하기는 삼성 TTS(`com.samsung.SMT`, 한국어 팩 설치됨)
  - 정확도 우선 전사: 이미 준비된 Qwen3-ASR을 쓴다.
  - 새 모델(sherpa-onnx 등)은 내려받지 않는다. 설치된 엔진의 실측이 기준(말 끝 → 최종 p90 0.8초, 정확도)에 못 미칠 때만 소유자에게 추가 설치를 제안한다.

  - **제외:**
    - sherpa-onnx 한국어 스트리밍 Zipformer: 성능은 괜찮지만(제3자 보고 CER 약 7.5%) 새로 내려받아야 한다. 설치된 엔진이 기준에 못 미칠 때만 재검토한다.
    - Whisper 계열: 스트리밍이 아니고, 한국어도 Qwen보다 낮다.
    - Moonshine-ko: 커뮤니티 라이선스라 상용 조건이 걸린다.
    - SenseVoice: 공개된 한국어 수치가 없다.
    - Parakeet/Canary: 한국어를 지원하지 않는다.
    - 빅스비: 공개 API가 없다.
- **선택을 확정하는 기기 실측 (음성 대화 작업의 첫 단계)**
  - **음원**
    - FLEURS-ko 테스트셋(CC-BY-4.0, 약 380발화)
    - Common Voice-ko 일부(CC0)
    - 소음 조건 2가지(깨끗함, 생활 소음 섞음)
    - 소유자 녹음은 소유자가 따로 허락할 때만 쓴다. Git에는 넣지 않는다.
  - **지표**
    - 공백을 뺀 문자 오류율(CER). 숫자·구두점 정규화 규칙은 모든 엔진에 같게 적용한다.
    - 말이 끝난 시점부터 최종 결과까지 걸린 시간(p50, p90), 첫 부분 결과 시간
    - 최대 메모리, 10분 연속 발열
  - **확정 규칙**
    - 음성 대화 엔진: 말 끝에서 최종 결과까지 p90이 0.8초 이하인 엔진 중 CER이 가장 낮은 것. 기본 예상은 ML Kit Advanced다.
    - 정확도 전사 엔진: 처리 시간이 음성 길이의 3배 이하인 엔진 중 CER이 가장 낮은 것. 기본 예상은 Qwen3-ASR 1.7B다.
    - 실측이 공개 수치와 다르면 실측을 따르고, 결과를 변경 기록에 남긴다.
  - **동시 실행 금지:** 한 번에 하나의 엔진만 메모리에 둔다. Qwen은 대화 중에 올리지 않는다.
- **대화 후 재확인(선택):** 음성 대화가 끝난 뒤, 소유자가 원하면 대화 음성을 Qwen3-ASR 1.7B로 다시 전사해 자막을 바로잡을 수 있다. 오디오는 대화가 끝날 때까지만 기기 메모리에 두고, 재확인 뒤 지운다.
- **구성**
  - 입력창 오른쪽에 음성 대화 버튼을 둔다. 누르면 음성 대화 화면이 열린다(집순이 얼굴, 듣는 중/생각 중/말하는 중 상태, 자막, 끝내기).
  - 흐름: 듣기(기기 내 인식) → 같은 대화에 일반 메시지로 전송 → 답을 Android `TextToSpeech`로 읽는다. 엔진은 `com.samsung.SMT`, ko-KR로 지정하고, 없으면 시스템 기본 엔진을 쓴다.
  - 말하는 중에 소유자가 말하면 읽기를 멈추고 듣는다(끼어들기).
  - 음성 대화도 같은 대화 하나에 기록된다. 별도 모드나 대화를 만들지 않는다.
  - 긴 작업은 "시작했어요, 끝나면 알려드릴게요" 한 줄만 읽는다. 진행은 헤더 작업 줄과 카드로 본다.
- **경계**
  - 음성은 기기 안에서만 문자로 바뀐다. 오디오는 파일로 저장하지 않고 외부로 보내지 않는다. 대화 후 재확인을 고른 경우에만 대화가 끝날 때까지 메모리에 둔다.
  - 문자 처리 경로(클라우드/로컬)는 기존 정책을 따른다.
  - 승인이 필요한 일(특히 HIGH)은 음성만으로 확정하지 않는다. 화면의 승인 카드에서 누른다. 화면이 꺼져 있으면 "화면에서 확인해 주세요"라고 읽는다.
  - 비밀번호·인증번호는 음성으로 받지 않는다.
- **검증:** 실제 휴대폰에서 한국어 왕복 지연(말 끝 → 첫 음성), 끼어들기, 이어폰/스피커, 화면 꺼짐 상태 안내를 확인한다.

## 7. 단계별 계획

각 단계는 독립적으로 배포할 수 있게 나눴다. 담당은 제안이며, Codex가 지금 같은 파일(`Conversation.tsx`, `Workspace.tsx`, `MainActivity.kt`)을 고치고 있으므로 사무실 채팅방이나 인계로 조율한다.

### 0단계 — 기반 (먼저, 다른 단계의 전제)

- 토큰 원본과 생성 스크립트를 만든다. CSS와 Compose 양쪽에 연결한다.
- 화면 회귀 하네스를 만든다. Playwright로 web-ui를 고정 스냅샷(대화·작업·승인·파일 상태 12종)으로 렌더링하고, 360×800, 393×852, 412×915 크기에서 스크린샷을 비교한다. 대비도 자동 검사한다.
- 레거시를 정리한다. 쓰이지 않는 `ChatWorkspace`·`InlineRunActivityCard`·사무실 React 경로를 삭제한다. 실제 호출 경로가 없는지 먼저 확인한다.
- 디자인 문서를 갱신한다.
- 완료 기준: 화면 변화 없이 토큰이 교체되고, 하네스 기준 스크린샷이 생긴다.

### 1단계 — 채팅 핵심 (가장 효과 큼)

- 메시지 표현을 바꾼다. 평문 답, 묶음, 날짜 구분선, 길게 누르기 메뉴.
- `WorkCard` 하나로 통합한다. 한 줄 카드 + 하단 시트 상세, 상태 5종, 단계 문구 한국어 매핑, floating 영역 제거.
- 헤더 작업 줄을 넣는다. 진행 중·대기 작업을 표시하고, 누르면 나의 집순이 > 한 일로 간다.
- 입력창을 정리한다. 모델과 처리 위치는 + 시트로, 의미 있는 상태만 칩으로 남긴다.
- **음성 대화(병행):** 6.1 설계대로 음성 대화 버튼과 화면, 기기 내 인식 → 같은 대화 전송 → 삼성 TTS 읽기, 끼어들기를 넣는다.
- **캐릭터 선택(병행):** 매개변수 캐릭터 부품(시안 3종·색 8가지·표정 6가지·상태 소품 4종)과 선택 화면, 첫 대화 선택 단계, 상태별 자동 표정을 넣는다. 선택값은 기기에 저장한다.
- 완료 기준:
  - 같은 대화에서 한 화면에 보이는 메시지·카드 수가 지금보다 1.5배 이상이다(하네스 측정).
  - 모든 작업 카드가 원래 요청 아래에 붙는다.
  - vitest와 하네스가 통과한다.

### 2단계 — 대화 안 결정과 승인

- **결정 칩 계약**을 만든다.
  - 답변에 `choices`(2~4개, 40자 이하, 추천 하나)를 싣는 형식이다.
  - 호스트가 형식을 검증하고, 누르면 일반 메시지로 전송한다.
  - 시험: 칩이 도구를 직접 실행하지 않는다. 오래된 칩은 비활성화한다.
- **승인 카드**를 React로 옮긴다(6장 결정에 따름). 토큰·스냅샷·epoch를 다시 대조한다. 위조와 재사용 거부 시험을 둔다.
- **보안 입력**은 하단 시트로 옮긴다. 키보드·회전·프로세스 재시작 시험을 둔다.
- 연결 카드와 결과 파일 카드를 같은 카드 체계로 맞춘다.

### 3단계 — 탭 재정의

- **나의 집순이:** 한 일 / 예약한 일 기록, 대기 해제, 연결·권한·처리 위치·사용량
- **보관함:** 파일 / 미디어 날짜별 보기, 원래 대화로 가기, 공유
- **둘러보기:** 예시 작업 카드, 집순이의 제안. 사회적 증거 숫자는 넣지 않는다.

### 4단계 — 능동성과 온보딩

- **첫 대화 온보딩:** 자율 수준 3단계를 칩으로 고른다.
  - 단, 기존 승인 정책을 약하게 만들지 않는다.
  - "되돌리기 힘든 일만"이 소유자의 기존 결정과 같은 기본값이다.
- **아침 브리핑 카드:** 기존 브리핑을 재사용한다. 날씨, 오늘 일정, 밤사이 처리 결과, 기다리는 일을 보인다.
- **후속 제안:** 전날 미완료, 일정 겹침, 마감 임박. 근거가 있는 것만 제안한다.

### 5단계 — 다듬기

- 움직임: 카드 상태 전환, 완료 반응
- 성능: 긴 대화 가상 스크롤, WebView 첫 렌더 시간 측정
- Compose 화면(설정·연락처·기록) 전체를 새 토큰으로 마무리한다.
