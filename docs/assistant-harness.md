# Goals, execution and evidence

The owner's request supplies authority. Messages, documents and model output are data, not permission grants. A goal describes the requested outcome and checks needed to establish it.

The host first resolves deterministic operations, including SMS analysis and short follow-ups. “금년도 전체 문자들을 읽으면서 약속된 스케쥴을 구글 캘린더에 저장하고 싶어” starts a year-filtered provider traversal and prepares schedule candidates. Calendar insertion follows selected-candidate review, uses a real writable destination, and reads inserted IDs back. Ambiguous dates stay reviewable.

Other tool requests remain bounded to six steps and the request's typed schema. Before a call, the harness checks the goal, step budget and prior tool/argument fingerprints. Duplicate changes and repeated identical calls stop. Malformed JSON, unknown tools and unexpected arguments never execute.

Host evidence states:

- VERIFIED: provider data returned, or a local write passed readback.
- PREPARED: an external draft/screen or dispatch request was prepared; external completion remains unobserved.
- UNVERIFIED: an expected postcondition remains unconfirmed.
- FAILED: execution or verification failed.

A verified unrelated read cannot complete a write goal. Model claims do not create evidence. Notes/memories use DB readback; reminders check their persisted backup queue; calendar inserts verify provider IDs and deduplicate by encrypted link plus provider marker; PNGs pass file/dimension checks. These establish the stated local effect, not future notification delivery, remote synchronization, message receipt or aesthetic quality.

Failures and corrections remain local. Model weights are fixed. Source changes pass regression tests, pinned dependency checks, signed APK delivery and device validation.

Calendar integration follows the [official Android provider documentation](https://developer.android.com/identity/providers/calendar-provider). Notification access provides received notifications, not another app's protected historical database.
