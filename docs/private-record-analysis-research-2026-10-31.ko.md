# 문자·대화·녹음의 실제 분석 역량 확장 조사

조사일: 2026-10-31 KST. 대상: ZipHap.Agent의 허용된 개인 자료 분석. 공개 논문·공식 오픈소스 자료와 앱 소스를 읽었으며 실제 개인 문자·녹음·계정 원문을 조회하거나 외부에 전송하지 않았다. **이번 확장은진행 중인 안정화 이후 별도 기능 빌드로 준비하며, 진행 중인 안정화의 소스·빌드·기기 창을 바꾸지 않는다.** 스킬 준비물은 격리 경로에 있으며 APK 포함·휴대폰 설치·모델 의미 평가의 성공을 뜻하지 않는다.

## 격리 구현의 현재 범위와 한계

도구6개와 번들 스킬3개, 원문 범위·실제 UTF-8 인용 검증, 질문별 조각 추출, 암호화된 진행 상태, 버전이 일치하는 이어가기, 원문 재조회와 상세 TXT 보고서의 생산 코드를 준비했다. 등록·실행기·권한·모드·의미 계획 도구 안내·취소·파일 선택의 원래 방 고정까지 격리된 통합본으로 연결 중이다. canonical 소스·APK·설치 성공과 구분한다.

한 번에는 실제 모델에 제공한 조각만 처리한다. 각 조각의 결과는 최대4개이며, 처리된 모든 바이트가 모든 관련 사실의 발견이나 올바른 해석을 보장하지 않는다. 전체 상세 결과는 암호화된 분석 기록에 남기고, TXT 파일에는20MiB 한도에서 항목 전체 단위로 수록하며 생략 수를 표시한다.  짧은 개요는 최대48개의 고르게 뽑은 색인에서 질문에 맞는 최대4개 항목을 모델이 선택한다. 색인을 줄여 읽었다면 결과에도 그 사실을 표시한다. **현재 조각별 추출과 제한된 개요 선택을 여러 문서 전체의 완전한 계층 종합·모순 해결로 홍보하지 않는다.** 긴 관계 추론의 실제 한국어 품질은 합성 정정·취소·후속 업무 사례의 실기 결과로 따로 확인한다.

완료는 선택한 저장 본문 전체가 처리되었다는 뜻이다. 일부 자료만 가져온 상태, 모델 응답 실패, 처리 상한은 별도로 남는다. 이어갈 저장 본문이 없는데 최초 캡처가 불완전한 경우에는 재개를 제안하지 않는다. 음성은 기존15초 디코더 구간에 묶으며 단어별 정렬·화자 구분·실제 음성 누락 여부는 검증하지 않는다. 모델 가중치를 재학습하거나 새 ASR 모델을 자동 설치한 변경이 아니다.

## 현재 가장 큰 병목

현재 채팅 도구는 자료를 조금 찾는 기능에 가깝다. **이미 저장한 전체 자료를 빠짐없이 읽고 종합하는 경로와 중요한 원문을 다시 확인하는 경로가 부족하다.** 임의의 RAG·MCP 패키지를 설치하거나 지침만 길게 만드는 것으로 이 차이가 채워지지 않는다.

| 현재 소스 경로 | 실제 읽는 범위 | 사용자가 기대하는 분석과의 차이 |
| --- | --- | --- |
| `get_sms_summary` | 권한이 허용한 SMS 개수·기간 통계와 최신 최대5개, 본문 각500자 | 전체 건수와 전체 본문 이해가 다르다. 현재 발췌 DTO에는 원 SMS ID도 없다 |
| `list_imported_conversations` | 완료된 가져오기 최대20개 메타데이터 | 목록을 읽어도 메시지의 약속·갈등·변경은 읽지 않았다 |
| `search_conversation_imports` | 검색어의 문자 일치로 저장 조각을 골라 상위3개, 반환 본문 각800자 | 같은 뜻의 다른 표현, 조각 뒤쪽, 뒤의 정정·취소, 검색어가 없는 관련 근거를 놓칠 수 있다 |
| `list_messenger_notifications` | 허용 앱의 현재 세션10분 이내 최대5개, 본문 각500자 | 과거 메신저 대화 전체에 대한 분석 기능이 아니다 |
| `list_audio_recordings` | MediaStore가 녹음으로 표시한 파일 메타데이터 최대20개 | 오디오를 열거나 듣거나 전사하지 않는다 |
| `search_audio_transcripts` | 이미 저장된 전사 노트에서 최대3개, 본문 각1000자 | 미전사 오디오·모든 전사 구간·특정 기록 전체 읽기가 아니다. 검색에 파일·전사 실행 ID 선택 인자도 없다 |
| 기존 PC 선택 자료 분석 | 선택한 표 파일6MiB 이하, 통계·회귀·클러스터·차트 또는 제한 SQL | TXT·문자 원문·전사·오디오를 그대로 분석하는 도구가 아니다 |

확인한 확장 전 기준 소스: `core/.../Tools.kt`, `app/.../tools/ToolExecutor.kt`, `imports/PhoneRecords.kt`, `imports/ConversationImport.kt`, `connections/PcToolClient.kt`. 이 기준 카탈로그는 도구82개·스킬21개다. 새 변경이 진행 중이므로 병합할 때 당시 실제 등록 상태를 다시 확인한다.

### 저장·화면 기능과 채팅의 실행 기능을 구분해야 한다

문자 전체 가져오기 화면은 이미 있다. `PhoneRecords.importSmsToRepository`는 최대100,000행/20MiB를 JSONL로 읽어 암호화 노트에 저장하며 본문·원본 ID·시각·유형을 보존한다. 그러나 채팅의 `get_sms_summary`는 이 저장 자료를 전수 종합하지 않는다. 별도 `SmsAnalysisController`는 최대100,000행/50MiB를 순회해 통계·고정 분류·일정 후보를 추출한다. 이는 자유로운 의미 분석이나 대화 전후 관계의 이해와 다르다.

가져온 대화는20MiB·최대2,000조각, 각8000자로 저장한다. 조각은 문자 길이로 나누며 메시지 경계나 앞뒤 겹침을 기준으로 나누지 않는다. 원문은 남지만 채팅에서는 상위 조각 일부800자만 보므로 뒤쪽의 중요한 문장이 전달되지 않을 수 있다.

녹음 전사 UI는 이미 있다. 사용자가 선택한 content URI를 `AudioChunkDecoder`가 최대100MB/2시간까지 읽고, `LocalAudioTranscriber`는15초 조각별 로컬 ASR 결과를 노트에 저장한다. 헤더의 실행 UUID와 시작–끝 초는 조각의 위치이며 단어별 정렬이나 검증된 화자 ID가 아니다. 현재 전사 노트에는 원본 파일 SHA·통일된 구조화 전사 manifest가 없고 검색 도구는 일부 노트만 반환한다. 등록된 채팅 전사 도구도 아직 없다. 다른 ASR 구현체가 존재해도 이 계약이 자동으로 확장되지는 않는다.

## 조사에서 확인한 설계 근거

### 긴 입력 전체를 한 번에 넣는 것만으로 충분하지 않다

Lost in the Middle은 필요한 정보의 위치에 따라 성능이 달라지고 중간 근거를 잘 활용하지 못하는 현상을 보였다. NoLiMa는 질문과 근거의 문자상 겹침이 작을 때 긴 문맥의 검색·추론을 평가하며 성능 저하를 보고한다. 따라서 문맥 길이를 늘렸다는 사실이나 특정 키워드 검색 성공만으로 변형된 질문과 전체 분석을 검증할 수 없다. 이 논문의 모델·영어 데이터 결과를 현재 한국어4B 폰의 실패율로 옮기지 않는다. [Lost in the Middle](https://arxiv.org/abs/2307.03172), [NoLiMa](https://arxiv.org/abs/2502.05167).

### 전체 흐름과 특정 질문은 서로 다른 읽기를 요구한다

SummN은 입력을 나누고 여러 단계로 요약하는 방법을 장문 문서·대화에 적용했다. QMSum은 회의에 대한 질문에 맞는 구간을 찾아 요약하는 과제를 다뤘다. GraphRAG 논문은 전체 자료의 공통 주제처럼 전역 질문에 일반적인 관련 조각 검색만으로 대응하는 한계를 설명하고 집단별 요약·종합 구조를 제안한다. 이 근거로 **전체 범위 분할 읽기와 질문별 원문 재조회 둘 다 필요**하다고 판단한다. 그래프 엔진 전체를 이 앱에 설치해야 한다는 결론은 아니다. [SummN](https://aclanthology.org/2022.acl-long.112/), [QMSum](https://aclanthology.org/2021.naacl-main.472/), [GraphRAG 원논문](https://arxiv.org/abs/2404.16130).

자유로운 중간 요약만 다시 요약하면 빠뜨린 근거가 나중에 돌아오지 않는다. 첫 단계는 서술형 요약과 함께 출처가 붙은 사건·요청·기한·결정·정정 후보를 남기는 편이 이 앱에 적합하다. 이는 논문 접근을 현재 저장 구조·작은 모델·업무 질문에 맞춘 구현 제안이며 실측된 우월성이 아니다.

### 사실성·시간·수정·모름을 따로 검사한다

FActScore는 긴 생성문을 원자적인 주장으로 나눠 근거가 뒷받침하는지 평가한다. LongMemEval은 정보 추출, 여러 세션의 연결, 시간 추론, 정보 갱신, 답할 수 없음의 인식을 구분한다. 이 관점을 최종 보고서의 주장별 출처와 합성 검증 사례에 적용하는 것이 유용하다. 공개 벤치마크 점수나 자동 평가기를 그대로 앱 성공률로 쓰지 않는다. FActScore의 사실 정밀도는 필요한 사실을 빠짐없이 찾는 재현율을 대신하지 않는다. [FActScore](https://arxiv.org/abs/2305.14251), [LongMemEval 논문](https://arxiv.org/abs/2410.10813), [공식 코드·평가 범위](https://github.com/xiaowu0162/LongMemEval).

## 우선 구현할 실제 기능

아래는 필요한 실행 역할이다. 개발 담당과 합의한 예정 이름은 다음과 같다. 이 문서 작성 시에는 아직 최종 registry·실행기·APK 검증 전이며, 이름만 문서에 넣어 실행 가능하다고 보고하지 않는다. 스킬의 새 도구 참조도 실제 등록 확인 뒤에 병합한다.

| 예정 도구 | 실제 연결할 역할 | 완료로 오해하지 않을 것 |
| --- | --- | --- |
| `list_analysis_sources` | 현재 허용 범위에서 저장된 자료의 메타데이터 목록 | 자료 개수·청크 수를 의미 분석으로 표시하지 않음 |
| `analyze_sms` | 질문과 허용된 기간에 맞춰 SMS를 분할 읽고 근거 있는 결과 생성 | 실행 상한까지 처리한 일부를 전체 SMS 분석으로 표시하지 않음 |
| `analyze_audio_transcript` | 선택한 전사 실행/자료를 질문에 맞게 분석 | 음성 목록이나 검색 발췌를 실제 청취·전사로 바꾸지 않음 |
| `analyze_conversation_import` | 선택한 가져오기 해시의 완료 원문을 분할 분석 | 특정 파일을 다른 메신저의 전체 과거 대화로 확대하지 않음 |
| `transcribe_recording` | 실제 녹음 목록에서 선택한 기록을 요청 범위에 묶어 기존 ASR로 전사 | 파일 목록·예약 상태를 전사 완료로 표시하지 않음 |
| `read_analysis_evidence` | 생성된 분석의 실제 근거 식별자로 상세 원문 재조회 | 요약 답변을 전체 상세 보고서·원문으로 대신하지 않음 |

### 1. 범위를 고정한 자료 목록과 원문 읽기

사용자가 허용한 출처·기간·방·프로젝트를 고정한 불변 snapshot/manifest를 만든다. 자료 ID·내용 버전 해시·총건수·총문자·시간 범위·정렬 기준을 보존한다. 취소·권한 해제·삭제·자료 변경 이후 이전 범위를 새 자료에 재사용하지 않는다.

전체 읽기는 마지막 위치로 이어갈 수 있는 페이지나 청크 단위로 제공한다. 가능하면 메시지 경계를 보존하고, 길어서 한 메시지를 쪼개면 같은 ID·연속 위치·잘림 상태를 남긴다. 특정 질문의 검색은 후보와 앞뒤 원문을 함께 읽을 수 있어야 한다. 원본을 다시 읽을 수 없는 요약만 반환하는 도구로 끝내지 않는다.

SMS에서 ID·대화 식별자를 새로 제공할 때 가린 전화번호 끝4자리만으로 사람을 합치지 않는다. 제공자 원본 ID와 필요한 경우 범위에 묶인 비식별 대화 키를 사용한다. 날짜가 바뀐 동일 본문이나 같은 문구의 다른 발신자를 중복으로 버리지 않는다.

### 2. 출처와 처리 범위를 보존하는 분할 분석

폰의 한 모델과 현재 토큰 예산 안에서 실제 원문을 순차로 읽는다. 각 청크에서 사용자의 질문에 관련된 주장·사건·약속·기한·정정 후보를 추출하고 출처 위치를 붙인다. 표현이 다르다는 이유로 검색에서 제외하지 않는다. 중간 판단의 자유도는 모델에 두고 호스트는 입력 범위·근거 위치·중복·실행 예산·취소·형식을 확인한다.

최소 결과 구조에는 다음 정보를 둔다. 모든 기록에 맞지 않는 필드는 비워 둘 수 있다.

- 처리 범위: 총/처리/남음 건수·청크·문자 또는 오디오 시간, 제외·실패 이유, 이어갈 위치.
- 출처: 원본 버전, 메시지·전사 조각 식별자, 실제 인용 위치, 관찰 시각과 기록 시각.
- 주장: 누가 무엇을 요청·설명했는지, 대상·사건, 근거 문장, 실제 사건 시각/불명확성, 정정·반박의 출처.
- 업무: 요청·제안·확정·취소·완료 등 근거에서 확인한 상태, 담당·기한, 확인이 필요한 부분.

고정된 분류 단어를 의도 해석기로 쓰지 않는다. 이 구조는 결과를 검토하기 위한 틀이며 질문마다 모든 칸을 억지로 채우지 않는다. 초기 몇 건만 처리했다면 전체 분석이 아니라 처리 범위의 결과를 돌려준다.

### 3. 병합과 핵심 원문 재확인

같은 원문 ID·위치의 반복 읽기와 겹친 조각은 중복 집계하지 않는다. 날짜·발신자·사건이 다르면 같은 문구라도 별도로 남긴다. 인물·사건 연결은 모델의 제안과 근거로 판단하고 이름이 비슷하다는 이유만으로 강제로 합치지 않는다.

정정은 같은 주제인지 원문을 비교한다. 기록 순서가 최신이라는 이유로 다른 사건의 사실을 덮어쓰지 않는다. 원문 시각과 발화 속 미래 일정, 전사 시각과 녹음된 사건 시각을 나눈다. 불일치하면 양쪽 근거를 보존하고 미해결로 둘 수 있다.

최종 핵심 주장과 담당·금액·기한·취소 여부를 원문과 다시 비교한다. 해석만으로 만들어진 항목은 지우거나 해석으로 표시한다. 최종 결과에는 근거를 따라갈 수 있는 식별자·시각과 처리 범위가 있어야 한다. 의사 결정에 꼭 필요한 원문을 못 읽었다면 그 한계를 먼저 밝혀야 한다.

전체 상세 분석·출처는 범위에 묶어 보존하고, 화면의 짧은 최종 답변은 그 보고서의 설명으로 다룬다. 답변이 짧아졌다고 이미 확인한 출처·분석 결과를 버리거나, 상세 보고서가 생겼다고 빠진 구간까지 처리했다고 말하지 않는다. 문자·바이트·시간 위치는 명시적인 단위와 원본 버전에 묶는다. Kotlin 문자열 위치와 UTF-8 바이트 위치를 혼용하지 않고 실제 원문 발췌와 일치하는지 검증한다.

## 녹음의 시간 근거와 화자 처리

현재 ASR을 바로 교체하기보다 **선택한 녹음과 전사 결과의 구조화 연결**부터 만든다. 원본 파일 ID/해시, 전사 실행·모델 버전, 전체 길이, 처리 구간·실패·중복·원문 조각을 manifest로 보존한다. ASR의 빈 출력·조각 누락·경계 반복을 숨기지 않는다. 한 조각을 재시도하면 같은 구간의 상태를 갱신하고 이전 결과와 버전을 구분한다.

15초 조각의 시작–끝은 대략적인 위치다. 단어별 시각이나 구간 안의 정확한 발화 시점을 만들어서는 안 된다. 실제 화자 분리가 없는 현재 출력에 사람 이름·화자 번호를 붙이지 않는다. 화자 분리 결과가 있어도 임의의 `SPEAKER_00`을 사용자 본인이나 특정 연락처라고 추측하지 않는다. 중요한 고유명사·금액·날짜·부정어·결정은 가능한 해당 구간 재생/정밀 전사로 확인한다.

WhisperX 논문은 VAD와 음소 강제 정렬로 장문 전사의 시간 정렬 문제를 다룬다. 현재 공식 저장소는 언어별 정렬 모델이 필요하고 겹말·화자 분리가 불완전하다고 명시한다. 화자 분리에는 Hugging Face read token과 해당 pyannote 모델 약관 동의가 필요하다. 라이브러리 코드는 현재 BSD-2-Clause이며 사용하는 가중치·종속 도구의 조건은 따로 확인한다. 따라서 필요하면 **선택된 PC의 로컬 정밀 전사 후보**로 제한 실험하고, 지금 폰에서 설치·한국어 정확도·화자 식별이 검증됐다고 말하지 않는다. [WhisperX 논문](https://arxiv.org/abs/2303.00747), [공식 구현·조건·한계](https://github.com/m-bain/whisperX).

whisper.cpp는 C/C++ 네이티브 대안이지만 기존 Qwen ASR/모델 관리/한 모델 RAM 정책과 별도 통합이 필요하다. 공식 tinydiarize 예시는 실험적 speaker segmentation이고 영어 모델 예시다. 이를 한국어의 검증된 다인 화자 식별 기능으로 홍보하지 않는다. [whisper.cpp 공식 저장소](https://github.com/ggml-org/whisper.cpp#speaker-segmentation-via-tinydiarize-experimental).

## 폰과 연결된 PC에 맞는 도입 범위

우선은 현재 Kotlin·암호화 저장소·로컬 모델을 사용해 자료 경계, 이어 읽기, 근거가 붙은 추출·종합·원문 재확인을 연결한다. 반복 구조를 참고하기 위해 Python/LangChain/GraphRAG 전체를 폰에 설치할 필요는 없다. GraphRAG 공식 저장소도 색인의 비용이 클 수 있고 예제 코드가 Microsoft의 공식 지원 제품이 아니라고 설명한다. [공식 GraphRAG 안내](https://github.com/microsoft/graphrag).

선택된 PC의 로컬 계산은 기존 페어링·동의와 필요한 자료 범위가 실제 연결된 경우에만 사용한다. 같은 논리·모델 계약으로 작은 작업을 나누며 실패 시 처리된 범위와 다음 위치를 보존한다. 현재 표 파일 분석 경로를 TXT 분석 도구처럼 가장하지 않는다. 원문을 PC 파일로 쓰지 않는 기존 조건, 취소·중복 방지·폰/PC 결과 일치를 지켜야 한다. NotebookLM 질문은 외부 클라우드 동작이므로 개인 녹음·문자 전송의 대체 경로로 자동 선택하지 않는다.

무료 공개 API를 더 붙이는 것은 이 개인 자료 병목의 우선 해법이 아니다. 필요했던 공개 취재 도구는 앞선 업무역량 확장과 별도로 유지한다. 개인 원문을 검색어로 보내거나 분석 서비스를 호출하지 않아도 이 파이프라인을 로컬로 만들 수 있다.

| 스킬 | 역할 | 후속 준비물의 참조 도구(추가 예정 포함) |
| --- | --- | --- |
| `message-analysis` | 문자·대화의 흐름·약속·정정·미해결 업무와 읽은 범위 보존 | 분석 출처 목록·SMS/가져오기 분석·근거 재조회, 기존 부분 조회·문서 생성 |
| `recording-analysis` | 메타데이터·전사·실제 청취 차이, 조각 시간·인식 한계·화자 근거 보존 | 실제 녹음 목록·전사·전사 분석·근거 재조회, 기존 전사 검색·문서 생성 |

기존 `evidence-research`는 공개 논문·공식 출처용이므로 개인 자료 종합에 덮어쓰지 않았다. `work-briefing`과 달리 메일·할 일의 업무 정리보다 원문 근거의 종합과 추론 한계를 다룬다. 담당이 확정한 새6개 이름을후속 준비물 본문·metadata에 연결했으나, **최종 카탈로그에 병합하려면 그6개의 실제 registry·실행기 연결을 먼저 확인해야 한다.** 이름의 존재를 새 API 설치나 성공으로 계산하지 않는다.

격리 정적 확인: 재개 버전 지침까지 포함한 새 본문3728/3436/3400bytes로 각6KiB 이하이며 기존21개+3개=24개, 전체 설명 목록1302/4000자다. 재개는 실제 결과의 `resumeArguments.analysisId`와 `expectedProcessedChunks`를 함께 사용한다. 완료된 저장 텍스트를 같은 버전으로 반복하거나 진행 버전을 추측해 올리지 않는다. SHA와 추가 항목은 같은 준비 경로의 `integration/skill-catalog-additions.json`, `skill-format-check.json`에 있다. 기존 카탈로그와 본문은 수정하지 않았다. 실제 등록·빌드·설치·기기·한국어 의미 평가는 별도다.

## 실제 완료 검증

합성 자료로 시작하고 개인 메시지 원문을 테스트·Git·개발 로그에 넣지 않는다. 사용자 승인된 실제 기기 검증은 최종 정확한 APK의 별도 단계다.

1. **범위와 이어 읽기:** 첫·중간·끝에 핵심 근거를 두고 전체 처리 수·기간·청크와 원문 인용이 일치하는지 확인한다. 상한·취소·자료 변경·권한 해제 시 일부 결과가 전체 완료로 바뀌지 않아야 한다.
2. **문맥의 변형:** 같은 목적을 다른 문장·간접 표현·복합 요청으로 묻고, 질문과 원문이 같은 단어를 쓰지 않아도 관련 근거를 찾는지 본다. 도구 이름 하나가 아니라 최종 목표의 충족을 평가한다.
3. **정정과 시점:** 과거 약속→변경→취소, 다음 달 계획, 다른 사건의 최신 메시지, 날짜 없는 발언을 섞는다. 최종 상태와 그 근거를 보존하는지 확인한다.
4. **중복·인물:** 재전송·겹친 전사 조각·같은 말의 다른 날·다른 발신자를 섞는다. 중복 집계와 잘못된 사람 합치기를 검사한다.
5. **전사 품질:** 무음·겹말·이름·금액·날짜·부정어·조각 경계를 포함한다. 구간 누락·시간 오차·발언 왜곡·화자 오귀속을 따로 측정하고 모르는 부분을 꾸미지 않는지 확인한다.
6. **사실성과 누락:** 주장별 원문 뒷받침 비율과 필수 사실·업무의 회수율을 각각 본다. 인용이 있다는 이유만으로 맞는 분석으로 채점하지 않는다. 모순 발견·근거 부족 시 보류·전체 처리율도 별도 기록한다.
7. **실행 연결:** 카탈로그·스킬 해시·실제 handler·모드/프로젝트 범위·취소·저장 증거를 검사한 뒤 release·서명·설치 해시를 남긴다. 이후 실제 모델의 한국어 업무 품질을 측정한다.

이 문서의 근거와 설계는 실제 소스 구현·검증을 위한 선택 기준이다. 스킬을 읽힌 사실이나 고정 JSON 형식 통과를 “문자와 녹음 분석을 학습했다”는 증거로 사용하지 않는다.

후속 감사: 대용량 보고서는20MiB 이내로 항목 전체 단위에서 제한하고 생략 수를 model context에도 보존한다. 모든 내부 조회도 원래 취소 가능한 Job에서 실행하며 감사 기록 오류가 구조화 결과를 손상시키지 않게 한다. 프로젝트 접근 정책이 작업 중 바뀌면 전체 scope를 관찰해 작업을 중단한다. 일반 메모 검색은 내부 collection 제외를 SQL LIMIT 전에 적용해 대량 분석 기록 때문에 정상 메모가 밀려 누락되는 회귀를 막는다. 실제 DB·KSP·휴대폰 성능·의미 품질 검증은 별도다.
