# 문맥 이해·취재 능력 개선을 위한 GitHub 조사

조사일: 2026-10-31 KST. 상태: **취재와 비교 실험 설계 완료, 최소 행동 루프의 우수성은 이 앱에서 아직 검증 전**.

## 판단

우선 시험할 방법은 짧은 능력 안내와 필요한 지침 읽기, 그리고 **도구 선택 → 실제 결과 관찰 → 다음 행동 판단**을 반복하는 구조다. 모든 요청의 행동·대상을 먼저 확정하고 최초 도구 집합에 묶는 단계를 기본 경로에서 완화하는 실험이 우선이다. 실행 인자·권한·실제 도구 범위·중복 실행·취소·실행 증거 검증은 도구 경계에 남긴다.

사용자가 지정한 업무 패턴·기간·예산 같은 목표 조건은 그대로 보존한다. 줄이려는 것은 앱이 추가한 분류·절차 부담이다. “조건을 지우면 모델의 이해력이 올라간다”, “스킬 설치로 학습이 끝났다”는 결론은 확인하지 않았다.

## 현재 앱에서 관찰한 것

기준 앱은 실제 설치1009, SHA256 `e0eb2de9ad50a3c9b38abf29db1145058d69e5160f07f325ad18c4381f0aa102`다. 고정 APK와 기기 설치 해시 일치를 확인했다. 비교 test APK는 `d1654a164ee375a5b18e0fb22fa2bc287355055fd3173583e84fe9318c9a71df`다. 기준 소스는 core364/app104=468개 JVM 검사와 release lint(오류0·경고91)를 통과했다. 이것은 문맥 이해 성능의 증거가 아니다.

현재 `ModelDecisionContract`의 등록 필드는10개지만 공통 필수는 `action/goal/targetType`3개이고 나머지는 행동별 필수다. “10개를 매번 전부 맞춰야 한다”고 기록하면 부정확하다. 모든 요청의 필수 선계획과 최초 `requiredTools`가 이후 도구 범위를 정하는 구조는 여전히 비교 대상이다.

같은 선계획 구조, 합성 요청·이력5개, CPU4스레드/문맥4096/출력384/thinking=false로 캐시 모델을 비교했다. 개인 자료 조회·실제 도구 실행·가중치 다운로드·기본 모델 선택 변경은 하지 않았다.

## 1차 원천에서 확인한 근거

### DeepAgents: 짧은 안내로 성능을 유지한 비교

[실제 변경·실험표 PR #5009](https://github.com/langchain-ai/deepagents/pull/5009)는 튜토리얼·예시를 줄이고 도구의 핵심 계약은 남겼다. 도구 설명만의 토큰은43%, 기본 프롬프트·todo 선택 기능을 포함한 전체 기본 입력은 약65% 줄었다. 36개 작업을3회씩4개 모델에서 비교한 보상 변화의95% 신뢰구간은 모두0을 포함했다. 일부 모델의 비용은 증가했다.

따라서 불필요한 안내를 줄여도 성능 유지가 가능하다는 근거다. 작은 Gemma의 정확도가 반드시 오르거나 모든 모델의 비용이 줄어든다는 증거는 아니다. 앱에서는 긴 공통 지침과 매번 필요한지 불명확한 선계획부터 별도 비교한다.

### Pi·smolagents: 다음 행동은 모델, 도구 검증은 실행기

[Pi 실행 루프](https://github.com/earendil-works/pi/blob/main/packages/agent/src/agent-loop.ts)는 결과를 다음 턴으로 전달하고, 실행 전 등록 도구 조회·인자 검증·차단 훅·취소를 적용한다. 기존 `badlogic/pi-mono` 주소는 현재 `earendil-works/pi`로 이동한다.

[smolagents 구현](https://github.com/huggingface/smolagents/blob/main/src/smolagents/agents.py)은 도구·관찰 반복을 기본으로 하고 별도 주기적 계획은 `planning_interval=None`이 기본이다. [개선 가이드](https://huggingface.co/docs/smolagents/en/tutorials/building_good_agents)는 도구의 유용한 출력·오류와 불필요한 모델 호출 감소를 강조한다.

두 구현은 사전 분류를 줄인 설계의 참고 근거다. 이 코드가 현재4B 폰에서 더 정확하다는 직접 실험은 아니다. Node/Python 프레임워크 전체를 Android에 설치하기보다 필요한 구조를 Kotlin 도구 실행기에 적용하는 편이 현실적이라는 판단이다.

### Agent Skills: 필요한 지침을 읽는 방식

[공식 형식](https://github.com/agentskills/agentskills/blob/main/docs/home.mdx)과 [Pi의 실제 로더](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/core/skills.ts)는 시작할 때 이름·설명만 제공하고 관련될 때 본문과 참고 자료를 읽는 방식을 사용한다.

앱에는 작은 능력 목록과 `load_skill/read_reference` 같은 제한된 읽기 기능을 제공하는 실험이 적합하다. 현재 연구 스킬을 읽히는 것과 모델 가중치 학습은 별개다. 스킬이 없는 항공 운임 연결을 자동으로 만들지는 않는다.

### llama.cpp·Gemma: 모델이 학습한 도구 형식 확인

[llama.cpp 문법 문서](https://github.com/ggml-org/llama.cpp/blob/master/grammars/README.md)는 schema가 출력 형식을 제한하며 일반 JSON schema는 prompt에 자동 삽입되지 않는다고 설명한다. 이 앱에서도 grammar를 적용한 뒤 형식은 통과했지만 의미 오류가 남았다.

[공식 function-calling 문서](https://github.com/ggml-org/llama.cpp/blob/master/docs/function-calling.md)는 native 형식과 generic 형식을 구분하며 generic 경로의 토큰·효율 비용을 설명한다. [Gemma 공식 예제](https://ai.google.dev/gemma/docs/capabilities/text/function-calling-gemma4)는 실제 tools를 chat template에 전달하고 호출 결과를 돌려주는 순환을 보여준다.

현재 JNI의 일반 `prepare_chat`은 `tool_choice=NONE`이며 실제 tools 배열을 전달하지 않는다. 도구는 호스트의 텍스트/독자 JSON 계약으로 안내된다. 이것이 의미 오류의 원인이라고 확정한 것은 아니지만, 분류 enum과 문장 지침을 더 늘리기 전에 native 도구 템플릿·결과 역할·호출 파서를 맞춰 확인할 구체적인 구현 지점이다.

### xLAM/APIGen-MT: 실제 행동 학습은 별도 과정

[Salesforce 공식 저장소](https://github.com/SalesforceAIResearch/xLAM)와 [APIGen-MT 논문](https://arxiv.org/html/2504.03601v1)은 검증된 다중 턴 행동 시연을 학습하는 접근을 제공한다. 논문의3B 모델은 BFCL v3 multi-turn56%, τ-bench 전체38.2%/항공32%로 보고된다. 다른 데이터·모델·평가의 수치를 이 앱 성공률로 옮길 수 없다.

이것은 스킬 문서를 읽힌 효과가 아니라 실제 행동 학습의 근거다. 현재 PC/폰에서 해당 학습이 가능하다고 확인하지 않았다. 코드·모델·데이터의 제품 사용 조건도 각각 확인해야 하므로 당장 설치할 상용 앱 대체 모델로 추천하지 않는다. 먼저 현재 업무의 실패 기록과 검증용 미사용 사례가 필요하다.

## 우선 적용할 설계와 검증 순서

1. **고정 기준:** 현재1009와 관련 모델 SHA를 유지한다. 새 PC 추론 wrapper가 들어가면 폰 비교는 명시적으로 `deviceOnly`를 사용한다.
2. **선계획 유무 A/B:** A는 현 sparse 선계획, B는 전역 `action/targetType` 필수 분류 없이 다음 도구 호출·필수 질문·답변을 선택하는 구조다. 같은 도구 설명과 자료를 제공한다. 도구 호출 자체의 입력 schema·권한·실행 증거 검증은 양쪽에 동일하게 둔다.
3. **지침 로딩 별도 비교:** B에서 전문 사전 주입과 능력 catalog→필요시 skill 읽기를 따로 비교한다. 첫 A/B부터 두 변경을 섞으면 원인을 분리할 수 없다.
4. **native 도구 형식:** 모델의 공식 chat-template 도구 전달·호출·결과를 별도 검증한다. 형식 유효성/의미 정확도/실행 성공을 나눠 기록한다.
5. **작업 결과 평가:** 기존16건 외에 보지 않은 한국어 정정·지시어·복합 조건을 포함한다. 첫 행동명보다 최종 조건 충족, 실제 작업 진전, 불필요한 질문, 허위 완료, 근거 일치와 지연을 채점한다. 모델·문맥·샘플링·총 출력/시간 예산을 고정하고 순서를 교차해 반복한다.
6. **검색 변동 분리:** 먼저 고정된 공개 자료와 합성 근무표 fixture로 비교하고 실제 웹·실운임 연결은 별도 통합 검사로 실행한다. 운임 도구가 없으면 그 한계를 정확히 말하는지가 평가 대상이지, 일반 검색을 실제 최저가 확인으로 인정하는 것이 아니다.

최소 행동 루프가 이 앱에서 더 낫다는 결과는 아직 없다. 새 구조를 전면 적용하거나 기본 모델을 바꾼 상태가 아니다. 현재 최신 합성 검증은 실패를 포함한 연구 체크포인트로 인계한다.
