땡큐캠핑 공개 숙소 상세에서 주소 지도와 캠핑장 배치도가 별도 요소인 것을 확인했다. 상세의 캠핑장 배치도 영역에서 같은 호스트의 JPG 원본을 확인했고 이미지 응답은 HTTP 200이었다. 날짜나 인원이 확정되지 않은 상세 페이지를 자리 재고 근거로 사용하지 않는다. [땡큐캠핑 공식 상세](https://m.thankqcamping.com/resv/view.hbb?cseq=2249)

1. 사용자가 승인해 저장한 출발 기준과 인원 구성으로 요청 날짜의 후보를 찾는다. 첫 메시지에 적용한 날짜·인원·거리 범위를 짧게 알린다. 진행 카드는 조사, 자리 확인, 사용자 인증 대기, 결제 확인, 예약 조회를 작업 증거에 따라 갱신한다.
2. 공식 예약처와 국내 판매 채널에서 같은 날짜·객실·인원의 재고를 대조한다. 사진, 이동시간과 기준점, 난방, 개별·공용 화장실, 온라인 결제와 필수 현장비를 같은 카드에서 비교한다. 바비큐 등 선택 비용은 별도다.
3. 선택한 예약을 준비하는 중에 다른 숙소의 상세 질문을 처리한다. 상세 조회는 선택한 예약을 바꾸지 않는다. 캠핑장은 공식 전체 배치도 원본과 해당 날짜의 실시간 자리 목록을 따로 확보한다. 휴대폰 문자 인식의 위치가 재고의 자리 번호와 정확히 한 번 일치한 곳만 표시한다. 작은 글씨, 중복 번호, 인식 실패는 번호 목록으로 선택하게 한다. 전체 배치도에서 시설·자리 동선을 함께 확인한다.
4. 사용자가 자리를 바꾸면 정확한 자리 및 요금·재고를 다시 확인한다. 이전 준비·승인·임시 점유를 새 자리의 것으로 재사용하지 않고, 이전에 잡힌 예약이 있으면 그 상태부터 확인한다.
5. 로그인·카카오 알림톡·문자 인증은 같은 대화에 연결된 휴대폰 보안 카드 또는 공식 인증 화면에서 받는다. 만료된 요청은 상태를 표시하고 공식 재전송으로 새 인증을 시작한다. 같은 예약 컨텍스트와 세션에서 재개한다.
6. 결제 전 카드에 업체·객실/자리·일정·입퇴실·인원·차량·최종 결제액·현장비·환불 규정·결제 기한과 확인된 결제 수단을 표시한다. 수단 버튼은 같은 준비 작업에 묶인 사용자 요청을 대화에 남기고 선택한 수단의 화면까지 연다. 결제 승인에 정확한 예약과 금액을 묶고, 금액·자리 변경 시 새 확인을 받는다. 최종 상태와 예약번호·영수증 재조회로 완료를 판정한다. 결제 응답이 끊겼으면 재조회 전 재전송하지 않는다.
7. 긴 조사에서는 확인한 객실과 비교 근거를 건별로 저장한다. 구간 한도나 사이트 응답 오류 이후 확인된 결과를 보여주고 남은 조회만 재개한다. A-02 선택 뒤 다른 숙소 질문과 전체 지도 요청, 자리 변경, 만료된 인증, 결제 실패·확정 재조회를 통합 시험한다. 실제 사이트 검증은 결제 전까지 진행하고 실제 결제는 그 거래의 별도 승인 뒤 실행한다.
8. 예약 준비 도중 차량번호 등 사이트에서 확인된 필수 변수가 새로 나오면, 완료한 단계와 입력 목적을 알려주고 그 항목만 요청한다. 답변 전후에 예약 대상·자리·인원·금액·기존 인증 결과를 같은 작업에서 유지한다. 기존 인증이나 임시 점유가 만료된 경우에만 해당 단계부터 다시 처리한다.
9. 공식 결제 화면은 같은 작업의 카드로 휴대폰에 넘기고, 가맹점·금액·대기 상태를 채팅에 남긴다. 약관 동의, 카드 입력, 카드사 인증은 사용자가 공식 창에서 처리한다. ‘다 했어요’와 결제창 닫기는 상태 재조회 신호다. 성공, 사용자 취소, 승인 지연, 미결제 예약, 세션 만료를 구분하고, 확인된 결제와 확정 예약을 각각 보고한다. 결제 입력과 화면의 카드·인증 정보는 모델, 로그와 채팅 미리보기에 남기지 않는다.
10. 예약 후처리는 같은 작업에 묶는다. 공식 예약 내역의 확정 상태, 예약번호, 자리·일정·인원과 결제 내역의 가맹점·금액을 각각 재조회한다. 주문번호나 결제창만으로 확정하지 않는다. 공식 확인서와 카드 영수증이 제공되면 같은 예약인지 대조하고 채팅에 첨부한다. 원본과 화면에서 만든 PDF를 구분하고 재조회할 수 있는 링크를 덧붙인다.
11. 체크인 위치·시간, 주차, 현장 규칙과 필요한 준비물을 공식 자료에서 찾아 함께 전달한다. 날씨는 조회 시각과 지역이 확인된 경우에만 반영한다. 사용자가 미리 지정한 개인 Google Calendar에 비공개·초대 없음으로 등록하고, 같은 예약의 기존 일정을 먼저 확인한다. 등록 권한이 없으면 캘린더를 연결할 수 있게 안내한다. 일정 ID·시각·공개 범위를 재조회한 뒤 일정 링크를 보여준다.
12. 모니모 등 카드사 앱을 요구하면 거래와 연계된 가맹점의 공식 모바일 결제 화면을 휴대폰에서 우선 사용한다. 현재 집합 WebView는 외부 앱 주소를 차단한다. 앱 간 복귀를 지원하는 가맹점·PG의 공식 흐름만 검증하며, 출처가 불명확한 앱 주소와 PC 세션의 인증 정보는 휴대폰에 복사하지 않는다. 휴대폰 브라우저에서 다시 열 때 같은 주문이 복구되는지 확인하고, 복구되지 않으면 새 결제 요청 전에 원래 예약 상태를 확인한다. 모니모 미설치·복귀 실패·취소·승인 지연에서 결제와 예약을 별도 재조회한다. [NICEPAY 결제창 연동](https://developers.nicepay.co.kr/docs/pg/auth/payment-window/) · [앱 간 결제 요구사항](https://developer.eximbay.com/eximbay/payment_linkage/api-app-to-app.html)

## 어떤 작업을 먼저 넘길지

1. **첫 구현 묶음은 P0-A와 P0-B다.** P0-A는 동일 숙소 가격을 확인하지 못한 실제 사례부터 다시 재현한다. P0-B는 채팅 안 보안 카드와 완료 후 상태 전환을 맡는다. 두 작업의 접점은 날짜·인원·요금과 인증 대기를 같은 작업에 저장하는 지점이다.
2. **두 번째 묶음은 P0-C와 P1-C의 중복 방지다.** 합성 사이트에서 한 번 내보냈는지 확인하고 공식 사이트에서는 허용 범위까지 시험한다. 가상의 견적과 실제 견적, 실제 예약 확인은 별도 기록으로 남긴다.
3. **세 번째 묶음은 P1-A·B·D·E·F다.** 숙소에서 검증된 거래 계약을 쇼핑·예약으로 옮기고, 디자인 마감과 기존 업무 회귀는 공통 영역 충돌을 피해서 검토한다. P2는 실제 사용 결과를 바탕으로 적용 순서를 조정한다.

### NOL 서비스 연결과 계정 찾기

- 구현: 앱 연결 목록의 NOL 서비스에서 채팅에 요청과 시작 안내를 추가하고, 같은 채팅의 보호 브라우저 카드에서 공식 로그인·계정 찾기·비밀번호 재설정을 이어간다. 카드에 현재 단계, 페이지에서 확인한 로그인 방식과 알림, 확인된 가려진 계정 정보를 보여준다. 접었다 열어도 같은 인증 화면으로 돌아간다. [NOL 공식 정책](https://policy.yanolja.com/policy) · [NOL 자주 묻는 질문](https://board.yanolja.com/faq/list/index.html)
- 정확한 NOL 마이페이지에서 로그인 상태를 확인한 뒤 브라우저 세션을 보존한다. 호환되는 공식 이메일 로그인 양식에서 소유자가 저장을 선택하면 기존 휴대폰 금고를 사용한다. 소셜 로그인과 추가 인증은 공식 화면에서 진행한다.
- 네이버 인증 화면에서 앱 승인, OTP, QR 및 새 추가 확인 화면을 구분한다. 표준 자동완성과 접근성 표현의 변형은 모의 페이지로 확인했다. 다른 서비스는 기존 공식 주소 정책 안에서 이 카드와 복귀 확인 흐름을 재사용할 수 있다. [네이버 2단계 인증 이용 방법](https://help.naver.com/service/5640/contents/18994)
- 실기 기준: 첫 연결, 만료된 인증번호와 다시 보내기, 비밀번호 재설정, 카카오 등 로그인 방식을 선택했을 때 같은 카드로 복귀, 앱 재시작 후 기존 계정 이용을 확인한다. PC 브라우저의 공식 페이지 시도는 HTTP 403으로 중단됐으며 모바일 실기와 타 서비스 적용은 남아 있다.
